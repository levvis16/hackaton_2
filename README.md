# CV-модуль для САТК на базе SiPeed Lichee Module 4A

Модуль компьютерного зрения для самоходного автоматизированного телеметрического
комплекса (САТК). Реализует полный цикл:

> **видео → предобработка кадра → детекция → формирование события → REST API → demo-интерфейс**

Целевая платформа — **SiPeed Lichee Module 4A** (SoC T-HEAD TH1520). Если платы нет,
модуль полностью запускается на ноутбуке в demo-режиме, а инструкция переноса на плату
приведена в разделе [9](#9-перенос-на-sipeed-lichee-module-4a).

## 1. Возможности

| Требование ТЗ | Реализация |
|---|---|
| Источник видео | Видеофайл, камера, RTSP, изображение, синтетический генератор (`app/input/video_source.py`) |
| Обработка недоступного источника | Ошибка логируется, состояние `error`, сервис **не падает** |
| Предобработка кадра | Letterbox-ресайз под вход модели, BGR→RGB, нормализация (`/255`), пропуск кадров (`frame_skip`) |
| CV-инференс | YOLOv8n в формате **ONNX** через ONNX Runtime (`app/inference/yolo_onnx.py`) |
| Детекция всех классов | 6 классов (см. [раздел 3](#3-классы-детекции)): сеть + эвристики OpenCV |
| Bounding boxes / класс / confidence | Отрисовка поверх кадра и в JSON-событии (`app/render.py`) |
| Формирование событий | `app/events/store.py`, антидубль по IoU и cooldown |
| Локальное хранение | JSONL-журнал `events/events.jsonl` + кадры событий `events/frames/*.jpg` |
| REST API | `/health`, `/status`, `/events`, `/events/{id}`, `/start`, `/stop`, `/config`, `/frame/latest`, `/metrics` |
| Demo UI | Web-интерфейс: видеопоток, рамки, журнал событий, метрики, кнопки Старт/Стоп (`static/`) |
| Метрики | FPS и latency (EMA / среднее / p95), счётчики событий и ошибок |
| Логи | Консоль + файл `logs/app.log`: запуск/остановка, ошибки, события, метрики |
| Edge-ready | Конфигурация `config.edge.yaml` + инструкция переноса и ограничения |

## 2. Архитектура и структура модулей

```
 ┌──────────────┐   кадр   ┌───────────────────────────────┐   детекции   ┌──────────────┐
 │ VideoSource  │─────────▶│      DetectionEnsemble        │─────────────▶│  EventStore  │
 │  (вход)      │          │  YOLOv8-ONNX + эвристики      │              │  (события)   │
 └──────────────┘          └───────────────────────────────┘              └──────┬───────┘
         ▲                          │   ▲                                        │
         │                          │   │ FPS / latency                          │ JSONL + кадры
         │                          ▼   │                                        ▼
 ┌───────┴────────┐         ┌────────────────┐          ┌──────────┐      ┌──────────────┐
 │   Pipeline     │────────▶│   Render/HUD   │─────────▶│ REST API │─────▶│   Demo UI    │
 │ (поток-цикл)   │  кадр с │  (рамки, метки)│  JPEG    │ FastAPI  │ HTTP │  (браузер)   │
 └────────────────┘  рамками└────────────────┘ (MJPEG)  └──────────┘      └──────────────┘
```

| Модуль | Назначение |
|---|---|
| `app/input/` | Источники видео (файл, камера, RTSP, изображение, синтетика) |
| `app/inference/` | Детекторы: `yolo_onnx`, `heuristics`, `mock`; таксономия классов; ансамбль |
| `app/events/` | Хранилище событий, антидубль, запись в JSONL и сохранение кадров |
| `app/pipeline.py` | Поток обработки: чтение → инференс → события → отрисовка → публикация кадра |
| `app/render.py` | Отрисовка рамок, классов, confidence и панели метрик |
| `app/metrics.py` | FPS, latency, счётчики (потокобезопасно) |
| `app/api/` | REST API и MJPEG-поток |
| `app/config.py`, `app/logging_conf.py` | Конфигурация и логирование |
| `static/` | Demo-интерфейс (HTML/CSS/JS, без внешних зависимостей) |
| `app/main.py`, `run.py` | Сборка FastAPI-приложения и точка запуска |

Расширение: чтобы **добавить новый класс/модель**, достаточно реализовать метод
`detect()` (интерфейс `app/inference/base.py`) и подключить детектор в
`app/inference/ensemble.py`. Переработка архитектуры не требуется.

## 3. Классы детекции

| Класс (событие) | Как реализован | Тип | Где демонстрируется |
|---|---|---|---|
| `person` — Человек | YOLOv8n (класс `person` COCO) | **Нейросеть** | demo-видео |
| `vehicle` — Транспорт/техника | YOLOv8n (`car`, `truck`, `bus`, `motorcycle`, `bicycle`, `train`) | **Нейросеть** | demo-видео |
| `smoke_fire` — Дым/огонь | HSV-эвристика (тёплые насыщенные тона + серые области), проверка текстуры области | Эвристика OpenCV | тестовая сцена `media/test_scene.jpg` |
| `spill` — Разлив/аномалия | HSV-эвристика (тёмная насыщенная жидкость / холодный разлив) | Эвристика OpenCV | тестовая сцена `media/test_scene.jpg` |
| `person_without_helmet` — Человек без каски | Оценка области головы человека (насыщенность/яркость «касочных» пикселей) | Эвристика OpenCV | demo-видео |
| `obstacle` — Препятствие | Зона перед камерой: пересечение рамки человека/техники с RO-зоной | Эвристика (правило) | demo-видео |

**Честное разделение**: классы `person` и `vehicle` распознаются **реальной нейросетью
YOLOv8n**. Классы `smoke_fire`, `spill`, `person_without_helmet`, `obstacle` —
**эвристики на OpenCV** (по ТЗ для этих сценариев допускается эвристика); они работают
на реальных кадрах, но имеют пороговую природу и не являются обученной моделью.

Используемая модель: `yolov8n.onnx` (YOLOv8-nano, ~12.8 МБ), вход `1×3×640×640`
(float32, RGB, `/255`), выход `1×84×8400`. Runtime — **ONNX Runtime** (CPU).

Чтобы сразу показать классы `smoke_fire` и `spill`:

```bash
python scripts/make_test_scene.py                 # создаёт media/test_scene.jpg
python run.py --config config.image.yaml          # эвристики на тестовой сцене
```

## 4. Быстрый старт

Требуется **Python 3.10+**. В примерах ниже команда `python` — на Windows её обычно
удобнее запускать как `py` (лаунчер Python).

```bash
# 1. Виртуальное окружение и зависимости
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate

pip install -r requirements.txt

# 2. Загрузка модели YOLOv8 (ONNX) и демо-видео
python scripts/download_model.py

# 3. Запуск сервиса (обработка стартует автоматически)
python run.py
```

Откройте в браузере:

* **Demo UI** — <http://127.0.0.1:8000/>
* **Документация API (Swagger)** — <http://127.0.0.1:8000/docs>

Полезные варианты запуска:

```bash
python run.py --source media/demo_person_bicycle_car.mp4 --conf 0.4
python run.py --source-type camera --camera-index 0        # веб-камера
python run.py --source-type synthetic                      # встроенный генератор кадров
python run.py --config config.edge.yaml --threads 4        # edge-профиль
python run.py --backend mock                               # проверка API без модели
```

> Если модель (`models/yolov8n.onnx`) отсутствует, модуль автоматически переходит в
> режим `mock`: цикл «детекция → событие → API/UI» продолжает работать.

Демонстрационный UI намеренно не отключает кнопки при загрузке страницы: кнопка
**«Стоп»** блокируется, пока обработка не запущена, и наоборот. На время запроса
кнопки блокируются и показывается статус («Запуск…»/«Остановка…»), поэтому
двойные нажатия не создают параллельных запросов.

**Корректная остановка.** Сервис завершается по `Ctrl+C` за ~1 секунду даже при
открытом MJPEG-потоке `/stream.mjpg`. Генератор кадров прекращает работу по
глобальному флагу остановки (`app/shutdown.py`), а сервер (`run.py`) использует
`timeout_graceful_shutdown` как страховку. Прежняя версия «зависала», потому что
uvicorn бесконечно ждал закрытия бесконечного MJPEG-соединения.

### 4.1. Автотесты

```bash
python -m unittest discover -s tests -v
```

Тесты не требуют файла модели (используется `backend=mock` и синтетические кадры)
и проверяют: таксономию классов, источники видео, формирование/дедупликацию событий,
эвристики `smoke_fire`/`spill`, REST API и живучесть сервиса при недоступном источнике.

## 5. Конфигурация

Основной файл — `config.yaml`. Все относительные пути разрешаются от каталога конфига,
что упрощает перенос на плату. Готовые профили: `config.image.yaml` (демо эвристик),
`config.edge.yaml` (запуск на плате).

| Секция | Ключ | Назначение |
|---|---|---|
| `app` | `host`, `port` | адрес и порт API |
| | `mode` | `demo` / `edge` |
| | `camera_id` | идентификатор камеры в событиях |
| | `autostart` | запускать обработку при старте сервиса |
| `video` | `source_type` | `file` / `camera` / `rtsp` / `image` / `synthetic` |
| | `path`, `camera_index`, `rtsp_url` | параметры источника |
| | `loop` | зацикливать видеофайл |
| | `target_fps` | ограничение частоты обработки (0 = максимум) |
| | `frame_skip` | пропуск кадров между обработками |
| | `process_width` | ширина кадра предобработки |
| `model` | `backend` | `auto` / `yolo_onnx` / `heuristics` / `mock` |
| | `path`, `labels` | путь к ONNX-модели и списку классов |
| | `confidence_threshold`, `iou_threshold` | пороги детекции |
| | `intra_op_num_threads` | число потоков ONNX Runtime (0 = авто) |
| | `providers` | провайдеры ORT (`CPUExecutionProvider`, NPU-провайдер платы) |
| `heuristics` | `smoke_fire`, `spill`, `helmet_check`, `obstacle` | включение эвристик |
| | `obstacle_zone` | зона перед камерой `[x1,y1,x2,y2]` в долях кадра |
| | `min_area_ratio` | минимальная площадь области для дыма/огня и разлива |
| `events` | `save_frames`, `frames_dir` | сохранение кадров событий |
| | `min_confidence` | порог для формирования события |
| | `cooldown_sec` | антидубль: не повторять событие по объекту чаще |
| | `store_path` | путь к JSONL-журналу |
| `logging` | `level`, `file`, `console` | логирование |

Параметры можно переопределять **переменными окружения** (`CV_SOURCE`, `CV_CONF`,
`CV_BACKEND`, `CV_PORT`, …) и флагами `run.py` (см. `python run.py --help`).

## 6. REST API

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка работоспособности |
| `GET` | `/status` | Статус обработки, источник, FPS, latency, модель |
| `GET` | `/events` | Список событий (фильтры `object_class`, `event_type`, `severity`, `since`, `limit`) |
| `GET` | `/events/{event_id}` | Конкретное событие |
| `GET` | `/events/{event_id}/frame` | Кадр события (JPEG) |
| `POST` | `/start` | Запуск обработки (можно передать новый источник) |
| `POST` | `/stop` | Остановка обработки |
| `POST` | `/config` | Изменение порога confidence, источника, frame_skip, target_fps |
| `GET` | `/frame/latest` | Последний обработанный кадр (JPEG) |
| `GET` | `/stream.mjpg` | Видеопоток с рамками детекций (MJPEG) |
| `GET` | `/metrics` | FPS, latency (EMA/avg/p95), счётчики событий |
| `DELETE` | `/events` | Очистка журнала в памяти |

Интерактивная документация — `/docs` (OpenAPI).

Примеры:

```bash
curl http://127.0.0.1:8000/status
curl "http://127.0.0.1:8000/events?object_class=person&limit=10"
curl -X POST http://127.0.0.1:8000/start -H "Content-Type: application/json" \
     -d '{"source_type":"camera","camera_index":0}'
curl -X POST http://127.0.0.1:8000/config -H "Content-Type: application/json" \
     -d '{"confidence_threshold":0.5}'
curl -X POST http://127.0.0.1:8000/stop
```

## 7. Формат события

Событие соответствует требованиям ТЗ (пример — `docs/event_example.json`):

```json
{
  "id": "evt_000001",
  "timestamp": "2026-11-23T19:45:46Z",
  "event_type": "person_detected",
  "object_class": "person",
  "confidence": 0.86,
  "bbox": {"x": 523, "y": 331, "width": 55, "height": 101},
  "frame_path": "events/frames/evt_000001.jpg",
  "camera_id": "cam_01",
  "severity": "medium",
  "status": "new",
  "raw_class": "person",
  "detector": "yolo_onnx",
  "source": "media/demo_person_bicycle_car.mp4",
  "track_id": 1
}
```

Поля `severity` и `event_type` назначаются по классу: `smoke_fire` → `critical`,
`spill` / `person_without_helmet` / `obstacle` → `high`, `person` → `medium`,
`vehicle` → `low`. Поля `raw_class`, `detector`, `source`, `track_id` — дополнительные
(удобны оператору), обязательный набор из ТЗ сохранён без изменений.

## 8. Demo-интерфейс

Web-интерфейс доступен на `/` и включает всё, что требует ТЗ:

* видеопоток (последний обработанный кадр) с **рамками, классом и confidence**;
* журнал событий (время, тип, класс, confidence, критичность) с фильтром по классу;
* просмотр кадра события по клику;
* текущие **FPS и latency** (текущее значение, среднее, p95);
* статус обработки `running / stopped / error`;
* кнопки **Старт** и **Стоп**, выбор источника, настройка порога confidence.

> Интерфейс реализован на чистом HTML/JS и раздаётся тем же FastAPI-сервисом
> (дополнительных зависимостей нет — удобно для edge). При необходимости его можно
> заменить на Streamlit-приложение, используя тот же REST API.

## 9. Метрики: FPS и latency

* **FPS** считается по скользящему окну 10 с (текущее значение) и как среднее за
  сессию (`fps_avg`).
* **Latency** — время инференса кадра (детекция): EMA, среднее и p95 по последним
  кадрам. Отображается в HUD поверх видео, в `/metrics` и в логах.

Автоматический отчёт:

```bash
python scripts/benchmark.py --duration 25
# → docs/BENCHMARK.md и docs/benchmark.json
```

### Измеренные значения (demo, ноутбук: i5-12500H, Python 3.13, 4 потока ORT)

| Метрика | Значение |
|---|---|
| Обработано кадров за 25 с | 279 |
| FPS (среднее за сессию, `fps_avg`) | **≈ 11.1** |
| FPS (текущий, скользящее окно 10 с) | ≈ 8.6 |
| Latency (среднее / p95) | **≈ 100 / 126 мс** |
| Пиковый FPS инференса (короткий замер) | ≈ 27 |
| Создано событий | 29 |

Полный отчёт: `docs/BENCHMARK.md`, машинночитаемый — `docs/benchmark.json`.

> Важно: на этом ноутбуке при длительной нагрузке включается **троттлинг**
> (схема питания «Сбалансированная»): кратковременно достигается ~27 FPS инференса,
> затем частота падает. Ограничение потоков ONNX Runtime (`intra_op_num_threads: 4`)
> снижает разброс и даёт стабильные ~11–15 FPS. На стационарной машине или с
> профилем «Высокая производительность» результат выше. Фактический отчёт для вашей
> среды формируется скриптом `scripts/benchmark.py`.

Целевой показатель ТЗ — не менее 15 FPS в demo/edge-режиме; на реальной плате
рекомендуется использовать NPU (см. ниже) и/или `frame_skip`.

## 10. Перенос на SiPeed Lichee Module 4A

### 10.1. Характеристики платформы (по официальной документации Sipeed)

| Параметр | Значение |
|---|---|
| SoC | T-HEAD **TH1520**, 4× RISC-V Xuantie C910 (RV64GCV) @ ~1.85 ГГц |
| NPU | **4 TOPS @ INT8** (до 1 ГГц), поддержка моделей TensorFlow / **ONNX** / Caffe |
| GPU | Imagination BXM-4-64 (OpenCL / OpenGL ES / Vulkan) |
| RAM | 4 / 8 / 16 ГБ LPDDR4X |
| Память | eMMC 8/32/128 ГБ + microSD |
| Камера | 4-lane MIPI CSI + 2× 2-lane MIPI CSI |
| ОС | Debian-based Linux (RISC-V), пользователь по умолчанию `sipeed` / `licheepi` |

Источник: официальная wiki Sipeed (Lichee Module 4A / Lichee Pi 4A). Точные
характеристики и поддерживаемые образы следует **сверить с актуальной документацией**
перед прошивкой.

### 10.2. Сценарий A — запуск на CPU (минимальный, без конвертации модели)

1. Прошить/загрузить актуальный Debian-образ для Lichee Pi 4A (см. документацию Sipeed).
2. Установить зависимости:

   ```bash
   sudo apt update
   sudo apt install -y python3 python3-venv python3-pip git libgl1 libglib2.0-0
   python3 -m venv .venv && . .venv/bin/activate
   pip install --upgrade pip
   pip install -r requirements.txt
   ```

3. Скопировать проект на плату (`scp`, git, USB-накопитель), загрузить модель:

   ```bash
   python scripts/download_model.py
   ```

4. Запустить сервис в edge-профиле:

   ```bash
   python run.py --config config.edge.yaml --threads 4
   ```

   Источник видео для платы — `camera` (MIPI CSI) или `rtsp`:

   ```bash
   python run.py --config config.edge.yaml --source-type rtsp \
       --source "rtsp://user:pass@<ip>/stream"
   ```

5. Открыть UI с другого компьютера: `http://<ip-платы>:8000/`.

> Примечание: колёса `onnxruntime` и `opencv-python-headless` для `riscv64` могут
> отсутствовать в PyPI. Тогда используются сборки/пакеты для RISC-V из репозиториев
> вендора (TH1520) — это указано как шаг проверки зависимостей.

### 10.3. Сценарий B — использование NPU (рекомендуется для целевого FPS)

NPU TH1520 поддерживает модели **ONNX**, но требует конвертации во внутренний формат
через вендорский SDK (компилятор моделей NPU от T-Head). Порядок действий:

1. Получить у вендора актуальную версию NPU-SDK/компилятора для TH1520 (см. документацию
   Sipeed/T-Head) и убедиться, что поддерживается YOLOv8-подобная архитектура.
2. Сконвертировать `models/yolov8n.onnx` (`1×3×640×640`) в формат NPU (INT8-квантование,
   при необходимости — с калибровочным набором кадров).
3. Запускать инференс через рантайм NPU, указав соответствующий провайдер в секции
   `model.providers` файла `config.edge.yaml` (либо добавив свой детектор-обёртку в
   `app/inference/`).
4. Сверить итоговые FPS/latency; при необходимости уменьшить `input_size`/`process_width`
   и включить `frame_skip`.

### 10.4. Ограничения и рекомендуемые параметры для платы

* CPU-инференс YOLOv8n@640 на 4 ядрах C910, как правило, **ниже 15 FPS** — для целевой
  частоты нужен NPU (INT8) либо меньший вход модели;
* рекомендуемые стартовые параметры (`config.edge.yaml`): `input_size: 640`,
  `process_width: 640`, `target_fps: 15`, `frame_skip: 1`, `save_frames: true`
  (на плате при нехватке места — `false`);
* запись кадров событий и JSONL-журнала выполняйте на eMMC/TF-карту с достаточным
  запасом по износу; при интенсивном потоке событий увеличьте `cooldown_sec`;
* для RTSP/MIPI-камеры держите `reconnect_attempts` > 0, чтобы сервис переживал
  кратковременные обрывы потока.

## 11. Известные ограничения

* Классы `smoke_fire`, `spill`, `person_without_helmet`, `obstacle` — **эвристики**, а не
  обученная модель: возможны ложные срабатывания/пропуски; пороги настраиваются в
  секции `heuristics`.
* Детектор `person`/`vehicle` использует COCO-классы → различает «транспорт» в целом,
  но не конкретные типы техники (для этого нужна своя размеченная модель).
* Модель `yolov8n.onnx` имеет фиксированный вход 640×640; для смены размера входа
  требуется повторный экспорт модели.
* API рассчитан на локальный запуск: `host` по умолчанию `0.0.0.0` для удобства
  демонстрации. Для эксплуатации ограничьте доступ (`127.0.0.1`/firewall/обратный прокси)
  — аутентификация в MVP не реализована.
* Автоматическое отслеживание объектов (трекинг) упрощённое: антидубль по IoU + cooldown.
* Производительность сильно зависит от CPU/питания; на ноутбуке возможен троттлинг.
